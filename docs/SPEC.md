# ElectricVision Track — Technical Specification

Reverse-documented from the codebase (no prior spec existed). Reflects the system as built. See
`docs/PRD.md` for the product/feature view.

## Stack

- **Next.js 16.2.6** (App Router), **React 19.2.4**. Note: `AGENTS.md` warns this Next.js version
  has breaking API changes from training-data expectations — consult
  `node_modules/next/dist/docs/` before assuming an API surface.
- **Firebase Client SDK v12** (`firebase`) — all tenant-scoped reads/writes from the browser,
  gated by `firestore.rules`.
- **Firebase Admin SDK v14** (`firebase-admin`) — server-only, used exclusively in
  `src/app/api/*/route.js` route handlers for operations that must cross tenant boundaries or
  otherwise can't be trusted to the client.
- **pdf-lib** + **@pdf-lib/fontkit** — client-side PDF generation/annotation (invoice attachments).
  A DejaVu Sans TTF is bundled under `public/fonts/` specifically because pdf-lib's built-in
  Standard-14 fonts can't render Romanian diacritics (ă, ș, ț).
- **recharts**, **date-fns**, **html5-qrcode**, **qrcode** — supporting libraries.
- **Deployment**: Firebase App Hosting, backend id `electric-vision-track`, root dir `/`.

## Multi-tenancy model

`tenantId` is always the tenant **owner's own Firebase Auth UID** — there is no separate tenant-ID
generation step; registering a new owner account and creating a new tenant are the same act.
Nearly all business data lives under `tenants/{tenantId}/{collection}/{docId}`.

A few collections sit outside that scoping:
- `users/{uid}` and `config/{docId}` — global, not tenant-nested (user profiles, the superadmin
  allowlist).
- `collaborations/{id}` — top-level, deliberately cross-tenant (see § Security model).

Field lists reflect what the current code actually reads/writes, not a formal schema (Firestore
is schemaless; these are conventions enforced only by application code).

## Security model

`firestore.rules` helper functions, in order of privilege:

- `isAuthenticated()` — base predicate, `request.auth != null`.
- `isOwner(userId)` — "is this your own document" (`request.auth.uid == userId`); used on the
  global `users/{uid}` profile. Distinct from the tenant *role* also called `'owner'`.
- `isSuperAdmin()` — `request.auth.uid` is listed in `config/superadmins`'s `admins` array.
  OR'd onto nearly every rule in the file, so a superadmin bypasses tenant scoping everywhere.
- `isTenantMember(tenantId)` — a `tenants/{tenantId}/members/{uid}` doc exists. Means "on the
  roster," regardless of role.
- `isTenantOwner(tenantId)` / `isTenantManager(tenantId)` — read that member doc's `role` field.
  **Supervisor and worker have no dedicated helper** — both collapse to plain `isTenantMember` at
  the rules layer (see § Known security gaps).

**General pattern** most tenant collections follow: read = `isTenantMember`, create/update/delete
= `isTenantManager`. Financial collections (`quotes`, `contracts`, `invoices`, `orders`,
`purchases`) tighten further — `isTenantManager` required even to *read*, delete restricted to
`isTenantOwner`.

**Two deliberate deviations**, both added this session:

1. **`tasks`/`timesheets` hours-approval state machine.** A task's `hoursStatus` field
   (`estimated → submitted → approved/rejected`) is more tightly gated than the rest of the task
   doc: any member can move `estimated ↔ submitted` (their own part of the flow), but only a
   manager can move `submitted → approved/rejected`, and that transition requires the *prior*
   value to already be `'submitted'` — a precondition specifically added to prevent a
   double-approve race (two managers, or a double-click, both succeeding and creating two
   timesheet entries). Every `hoursStatus` read in the rule uses `.get(field, default)`, not
   direct field access — tasks created before this feature have no `hoursStatus` field at all, and
   direct access on a missing key throws, which would otherwise silently strip plain members
   (though not managers, who fall through a different branch) of the ability to edit any
   pre-existing task. `timesheets` creation was tightened from "any member" to manager-only in the
   same change, closing a gap where a worker could self-log arbitrary hours with no oversight.
2. **`collaborations` is server-write-only.** `allow create, update, delete: if false` — all
   writes go through `/api/collab/create` and `/api/collab/resolve` using the Admin SDK, because
   the operation is inherently cross-tenant (Company A writing something that affects Company B)
   and can't be expressed as "does the caller own this document" in rules.

**`notifications`**: read/update/delete restricted to `resource.data.recipientUid ==
request.auth.uid` (recipient only); create open to any tenant member.

### storage.rules (full)

```
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /tenants/{tenantId}/files/{allPaths=**} {
      allow read: if request.auth != null;
      allow write: if request.auth != null && request.resource.size < 25 * 1024 * 1024;
    }
  }
}
```

### Known security gaps

Documented, not fixed — flagged during this session's work and left as explicit tradeoffs or
follow-up items rather than silently patched:

- **`storage.rules` read is not tenant-scoped.** `allow read: if request.auth != null` means any
  authenticated user on the platform (any tenant) can read any *other* tenant's files if they know
  or guess the storage path. Writes are similarly open (any authenticated user, any tenant, can
  write under any `tenants/{tenantId}/files/` path) — only file size is checked, not which tenant
  the caller belongs to.
- **Supervisor has no rules-layer identity.** The owner/manager/supervisor/worker distinction that
  matters in the UI (nav visibility) only partially matters in the database — supervisor is
  rules-equivalent to worker.
- **`/stocks`, `/inventory`, `/contacts` have no client-side route guard.** `Layout.js`'s
  redirect-on-unauthorized logic only covers `/companies` (owner-only) and the financial route
  group. A worker who navigates directly to these URLs sees live controls that will fail at the
  Firestore-rules layer on submit, with no user-facing error — the pages `console.error` and stop,
  the modal or form just silently doesn't save.
- **Global `users/{uid}` update rule has no superadmin bypass**, despite `/admin/users` offering a
  client-side action to reassign a user's role/tenant using the client SDK — worth verifying this
  action actually succeeds in practice, or whether it needs to move server-side (Admin SDK) like
  the collaboration writes do.

## Conventions

- **Data access**: `src/lib/firestore.js` exports the standard helper set —
  `addTenantDoc`/`setTenantDoc`/`updateTenantDoc`/`deleteTenantDoc`/`getTenantDoc`/
  `getTenantCollection`/`onTenantDocSnapshot`/`onTenantCollectionSnapshot`/`batchWriteTenantDocs`
  for tenant-scoped data, plus `getGlobalDoc`/`setGlobalDoc`/`getGlobalCollection`/
  `onGlobalCollectionSnapshot` for the few global collections. New pages should use these rather
  than calling `firebase/firestore` directly. Note: `batchWriteTenantDocs` only targets one
  collection per call — a write that must atomically touch two different collections (e.g. the
  task-approval flow's task-update + timesheet-create) needs a raw `writeBatch()` instead; see
  `src/app/tasks/page.js`'s `handleApproveHours` for the pattern.
- **Role gating**: use `useTenantRole()` (`src/hooks/useTenantRole.js`), which subscribes to the
  caller's own `tenants/{tenantId}/members/{uid}` doc — the same document the security rules
  check. Do **not** gate UI on `user.role` from `useAuth()`/`AuthContext`, which sources the
  *global* `users/{uid}` doc; the two can drift (kept in sync only by the invite flow), so a
  button gated on the wrong source can be visible-but-403 or hidden-but-actually-allowed.
- **Notifications**: `src/lib/notifications.js` (`createNotification`/`markNotificationRead`/
  `markAllRead`/`subscribeNotifications`) + `NotificationContext` for the bell UI. New producers
  just call `createNotification(tenantId, { recipientUid, type, title, body, link })`.
- **i18n**: `useI18n()` from `src/lib/i18n`, with every key present in both `en.json` and
  `ro.json`. No hardcoded user-facing English strings in new code — this was a recurring finding
  during this session's own reviews.
- **Multi-collection lookups by ID**: the established pattern is to load the referenced collection
  into local state via `onTenantCollectionSnapshot` and resolve with `.find()`, not to store
  denormalized display strings on the referencing doc (e.g. sites store `workerIds: []`, worker
  names are resolved client-side from the loaded `workers` list — not a `workerNames: []` array).
